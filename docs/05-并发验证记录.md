# 并发选课验证记录

> 目标：证明"最后一个名额被 N 个人同时抢"时，容量绝不超卖、`selected_count` 与 `enrollment` 记录数始终一致，并且失败请求能快速拿到中文原因而不是超时。

## 一、验证环境

| 项 | 值 |
|---|---|
| 后端 | Spring Boot 3.2 / JDK 17 字节码，MySQL 8 InnoDB |
| 连接池 | HikariCP `maximum-pool-size = 20` |
| 压测脚本 | `scripts/concurrent_test.py`（标准库 urllib + 栅栏同步发压） |
| 隔离级别 | MySQL 默认 REPEATABLE READ |
| 数据库 | `course_selection`，2000 学生 / 400 教学班 |

## 二、第一轮：发现"集体超时"

```text
[3/4] 30 个请求同时发出 …
TimeoutError: timed out        # 30 个请求全部 20s 超时
耗时 20.10s / 成功 0 / 40002 0
```

客户端全部超时，但数据库最终只涨了 1 个名额。说明**扣减逻辑没超卖，但请求链路被卡住了**。

`jstack` 抓到的关键栈：

```text
com.zaxxer.hikari.pool.HikariPool.getConnection
  <- com.usst.course.service.EnrollmentLogService.recordFailure
  <- com.usst.course.service.EnrollmentService.enroll
```

MySQL `information_schema.processlist` 同时显示 19 条连接停留在同一条
`UPDATE teaching_class SET selected_count = selected_count + 1 WHERE id = ? ...`，日志里失败请求的 `cost_ms` 全是 `30080`（正好是 `innodb_lock_wait_timeout`）。

### 根因

失败日志在**持有教学班行锁的事务内部**用 `REQUIRES_NEW` 另开事务写入：

1. 20 条连接全部进入选课事务，19 条在等同一行的行锁；
2. 持锁线程抛业务异常后要写失败日志，`REQUIRES_NEW` 需要**第二条连接**；
3. 连接池已被占满 → 持锁线程等连接，其余 19 条等它释放行锁 → 互相等待，直到锁等待超时。

即：**连接池 + 行锁的反向依赖**，不是超卖问题，但会把接口打成超时。

## 三、修复

- `EnrollmentService` 去掉方法级 `@Transactional`，改用 `TransactionTemplate` 显式控制事务边界；
- 校验失败直接抛出，事务在 `transactionTemplate.execute` 内回滚并**归还连接**；
- 失败日志在事务结束之后写（`EnrollmentLogService.recordFailure` 仍是 `REQUIRES_NEW`，但此时已无行锁、无挂起事务）；
- 新增 `config/TxConfig` 注册 `TransactionTemplate`。

```java
try {
    return transactionTemplate.execute(status -> doEnroll(studentId, classId, idemKey, begin));
} catch (BizException ex) {
    // 事务已回滚、连接已归还，此处写日志不会再与行锁互相等待
    logService.recordFailure(studentId, classId, "ENROLL", ex.getCode(), ex.getMessage(), idemKey, cost);
    throw ex;
}
```

> 重启时必须重新打包：本次第一轮的进程仍是修复前的 `.class`（源码 11:22 修改，进程 11:17 启动），所以磁盘上的代码是对的、跑起来的仍是旧逻辑。`mvn -DskipTests package` 后重启即可。

## 四、第二轮：修复后复测

构造一个容量 1、时间位图为 0 的观察用教学班，30 名学生同时抢：

```text
[3/4] 30 个请求同时发出 …
[4/4] 耗时 0.28s
容量            : 1
成功选课        : 1
返回 40002      : 28          # 名额已满
其他失败        : 1           # 40007 低年级不可跨选，正常业务拦截
selected_count  : 1
实际记录数      : 1
结论            : [PASS] 无超卖，数据一致
```

重复一次（重置该班后）：`耗时 0.38s`，1 成功 / 29 命中容量或规则拦截，结论同样 `[PASS]`。

判定条件（脚本内对账，三项同时成立才 PASS）：

1. `teaching_class.selected_count == COUNT(enrollment WHERE status='SELECTED')`
2. `selected_count <= capacity`
3. 成功响应数 == `selected_count` 的增量

## 五、附带的脚本修正

- `concurrent_test.py` 中 `COUNT(*)` 返回字符串，与整数比较导致"数据正确却判 FAIL"，已转为 `int`；
- 结论输出改为 ASCII 标记 `[PASS] / [FAIL]`，并统一 `sys.stdout` 为 UTF-8，避免 Windows GBK 控制台抛 `UnicodeEncodeError`；
- 压测数据（临时教学班 401、压测选课记录与日志）已清理，教学班 383 恢复为容量 30 / 已选 29。

## 六、结论

- 30 并发抢 1 个名额：**1 成功、0 超卖**，库存与记录数完全一致；
- 修复后单次请求 P99 在亚秒级，不再出现连接池互相等待；
- 容量正确性的兜底仍是那条带条件的 UPDATE，与事务边界、日志写法无关；但**事务边界决定了它会不会被日志拖死**。
